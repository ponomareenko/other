## Тестирование: ожидаемый и фактический результат

### Тестирование — Testing

Деятельность по оценке качества системы и обнаружению дефектов. Включает изучение требований, подготовку проверок, их выполнение и анализ результатов.

### Ожидаемый результат — Expected Result

Поведение системы, которое должно наблюдаться при заданных условиях согласно требованиям или другим согласованным основаниям.

### Фактический результат — Actual Result

Поведение системы, которое наблюдалось во время проверки.

### Дефект — Defect / Bug

Недостаток системы, из-за которого она может не выполнять установленные требования.

### Тестовый сценарий — Test Scenario

Ситуация или последовательность действий, которую необходимо проверить. Например: отправка заявки с сайта и создание сделки в CRM.

### Тестовые данные — Test Data

Значения, используемые при проверке: например, имя, телефон, сумма или валюта.

### Сквозное тестирование — End-to-End Testing / E2E

Проверка полного сценария через связанные компоненты системы. Например: форма сайта → интеграция → сделка в CRM.

### Повторное тестирование — Retesting / Confirmation Testing

Повторная проверка ранее обнаруженного дефекта после исправления, чтобы подтвердить, что проблема устранена.

## Позитивные, негативные и граничные проверки

### Позитивное тестирование — Positive Testing

Проверка работы системы с допустимыми данными и при предусмотренных действиях пользователя.

### Негативное тестирование — Negative Testing

Проверка реакции системы на недопустимые данные или действия. Проверка пройдена, если система правильно обработала такую ситуацию.

### Граничное значение — Boundary Value

Значение на границе диапазона или непосредственно рядом с ней. Например, при допустимом количестве от 1 до 100: 0, 1, 2, 99, 100 и 101.

### Анализ граничных значений — Boundary Value Analysis

Техника тест-дизайна, при которой проверки выбирают на границах диапазонов и около них.

### Класс эквивалентности — Equivalence Partition

Группа значений, для которых ожидается одинаковый характер обработки системой.

Например: целые числа от 1 до 100 — допустимые значения. Для проверки группы выбирают отдельные значения, а не перебирают каждое.

### Валидация входных данных — Input Validation

Проверка соответствия введённых данных установленным правилам: обязательности, типу, формату и допустимому диапазону.

### Тест-дизайн — Test Design

Определение проверок, тестовых данных и ожидаемых результатов, которые помогут оценить работу системы.

## Описание дефектов

### Баг-репорт — Bug Report / Defect Report

Описание дефекта, содержащее сведения для его воспроизведения, анализа и проверки исправления.

### Окружение — Environment

Условия, в которых проводилась проверка: среда приложения, браузер, операционная система, устройство и другие значимые параметры.

### Предусловия — Preconditions

Состояние системы и необходимые условия, которые должны быть выполнены до начала шагов проверки.

### Шаги воспроизведения — Steps to Reproduce

Последовательность конкретных действий, позволяющая получить описанную проблему.

### Повторяемость — Reproducibility

Возможность повторно получить проблему в указанных условиях. Частоту воспроизведения полезно выражать числом успешных воспроизведений относительно количества попыток.

### Подтверждения — Evidence

Материалы, показывающие проблему и помогающие её исследовать: скриншоты, записи экрана, запросы, ответы и фрагменты логов.

### Логи — Logs

Записи событий системы, которые помогают установить, какие действия происходили, когда и с каким результатом.

### Идентификатор операции — Transaction ID

Значение, позволяющее найти конкретную операцию в системе. У мерчанта и платёжного провайдера одна операция может иметь разные идентификаторы.

### Гипотеза о причине

Предположение о том, почему возникла проблема, которое ещё необходимо проверить.

## Серьёзность и приоритет дефектов

### Серьёзность — Severity

Степень влияния дефекта на работу системы, пользователей и бизнес. При оценке учитывают нарушение функций, целостности данных и другие последствия.

### Приоритет — Priority

Относительная срочность исправления дефекта с учётом его влияния, сроков, рисков и текущих задач.

### Критический дефект — Critical Defect

Дефект с особо серьёзными последствиями согласно принятой в команде шкале. Например, он может приводить к потере денег, повреждению важных данных или недоступности основной функции.

### Обходной путь — Workaround

Временный способ выполнить задачу, несмотря на существующий дефект. Обходной путь не устраняет причину проблемы.

### Масштаб влияния — Scope of Impact

Охват проблемы: какие пользователи, операции, платформы, гео или компоненты системы затронуты.

### Целостность данных — Data Integrity

Корректность, полнота и согласованность данных при их хранении и обработке.

## Повторное и регрессионное тестирование

### Повторное тестирование — Retesting / Confirmation Testing

Проверка после исправления дефекта, направленная на подтверждение того, что исходная проблема устранена.

### Регрессионное тестирование — Regression Testing

Тестирование после изменений, направленное на обнаружение дефектов в ранее работавшей функциональности, которые могли возникнуть из-за этих изменений.

### Регрессия — Regression

Ухудшение ранее работавшего поведения системы после изменений. В разговорной практике этим словом также называют регрессионное тестирование, поэтому значение зависит от контекста.

### Анализ влияния изменений — Change Impact Analysis

Определение компонентов, функций и сценариев, которые могут быть затронуты изменением, чтобы выбрать необходимые проверки.

### Область проверки — Test Scope

Набор функций, сценариев и условий, которые входят в конкретную проверку.

### Тестирование на основе рисков — Risk-Based Testing

Подход, при котором приоритет и глубину проверок определяют с учётом вероятности проблемы и серьёзности её последствий.

## Чек-листы и тест-кейсы

### Чек-лист — Checklist

Краткий список проверок, по которому можно отслеживать, что проверено и с каким результатом.

### Тест-кейс — Test Case

Описание конкретной проверки, включающее необходимые условия, входные данные, действия и ожидаемые результаты.

### Идентификатор тест-кейса — Test Case ID

Уникальное обозначение тест-кейса, позволяющее ссылаться на него в результатах проверок и баг-репортах.

### Набор тестов — Test Suite

Группа тест-кейсов, объединённых по определённому признаку: например, проверки формы заявки или сценариев пополнения баланса.

### Выполнение тестов — Test Execution

Проведение подготовленных проверок с фиксацией фактических результатов.

### Статус проверки — Test Status

Отметка о результате или состоянии выполнения проверки. Например: Passed — пройдена, Failed — не пройдена, Blocked — выполнение заблокировано.

### Заблокированная проверка — Blocked Test

Проверка, которую невозможно выполнить из-за препятствия, например недоступности тестовой CRM. Это само по себе не означает, что проверяемая функция работает неправильно.

## Проверки интерфейса и API

### Пользовательский интерфейс — User Interface / UI

Элементы, через которые пользователь взаимодействует с системой: страницы, формы, поля, кнопки и сообщения.

### API — Application Programming Interface

Интерфейс, через который программы или компоненты системы взаимодействуют друг с другом по определённым правилам.

### Запрос — Request

Сообщение, которое клиент отправляет серверу для получения данных или выполнения действия.

### Ответ — Response

Сообщение сервера с результатом обработки запроса.

### Endpoint

Адрес конкретного ресурса или операции API. Для точного указания операции обычно приводят HTTP-метод и путь, например POST /api/orders.

### Тело запроса — Request Body

Данные, передаваемые в запросе, например JSON с товаром и количеством.

### Тело ответа — Response Body

Данные, возвращаемые сервером, например сведения о созданном заказе или описание ошибки.

### Клиентская валидация — Client-Side Validation

Проверка данных на стороне клиента, например в браузере перед отправкой формы.

### Серверная валидация — Server-Side Validation

Проверка данных на сервере перед выполнением операции. Она необходима независимо от ограничений интерфейса.

### Network

Вкладка инструментов разработчика браузера, позволяющая исследовать сетевые запросы и ответы.

### Postman

Инструмент для отправки API-запросов, просмотра ответов и организации проверок API.

## HTTP: методы и коды ответа

### HTTP — Hypertext Transfer Protocol

Протокол обмена запросами и ответами между клиентом и сервером.

### HTTP-метод — HTTP Method

Обозначение действия, запрашиваемого у сервера, например GET, POST, PUT, PATCH или DELETE.

### HTTP-код ответа — HTTP Status Code

Трёхзначный код, сообщающий результат обработки запроса на уровне HTTP.

### Бизнес-статус — Business Status

Состояние операции в предметной области системы, например queued, processing, succeeded или failed. Набор статусов определяется конкретной системой.

### Асинхронная обработка — Asynchronous Processing

Обработка, при которой результат операции может появиться позже первоначального ответа на запрос.

### Очередь — Queue

Механизм хранения задач или сообщений до их последующей обработки.

### Аутентификация — Authentication

Проверка того, кем является участник взаимодействия, например с помощью токена доступа.

### Авторизация — Authorization

Проверка того, какие действия разрешены участнику взаимодействия.

### Таймаут — Timeout

Истечение времени ожидания. Таймаут сам по себе не доказывает, что операция не была выполнена.

### Контракт API — API Contract

Описание правил взаимодействия с API: методов, адресов, полей, форматов, ответов и ожидаемого поведения.

## Диагностика: Network и логи

### Диагностика — Troubleshooting

Последовательное исследование проблемы, позволяющее определить условия её возникновения и сузить поиск причины.

### Network

Вкладка инструментов разработчика браузера, показывающая сетевые запросы браузера, их параметры, ответы и время выполнения.

### Payload

Данные, передаваемые в запросе. В инструментах браузера раздел Payload может содержать JSON, поля формы и другие отправленные значения.

### Логи — Logs

Записи событий системы с информацией, полезной для анализа её работы: временем, результатами операций, ошибками и идентификаторами.

### Идентификатор запроса — Request ID

Значение, используемое для поиска событий, связанных с конкретным запросом. Его наличие и передача между компонентами зависят от реализации.

### Корреляционный идентификатор — Correlation ID

Идентификатор, позволяющий связать несколько запросов или событий одного процесса между компонентами системы.

### Временная метка — Timestamp

Запись времени события. Для сопоставления событий важно учитывать часовой пояс и возможные различия часов систем.

### Первопричина — Root Cause

Основная причина возникновения проблемы, устранение которой предотвращает её повторение при соответствующих условиях.

### Гипотеза — Hypothesis

Проверяемое предположение о причине проблемы, которое ещё не подтверждено достаточными данными.

## Основные платёжные операции

### Мерчант — Merchant

Бизнес, принимающий платежи за свои товары или услуги. В контексте вакансии это может быть оператор iGaming-платформы.

### Pay-in

Операция внесения денег пользователем в систему мерчанта, например пополнение игрового баланса.

### Pay-out

Операция выплаты денег пользователю, например вывод средств с игрового баланса.

### Возврат — Refund

Операция полного или частичного возврата ранее принятого платежа, связанная с исходной операцией.

### Платёжный провайдер — Payment Service Provider / PSP

Организация, предоставляющая услуги по приёму или отправке платежей. Конкретные функции зависят от провайдера и интеграции.

### Доступный баланс — Available Balance

Сумма, которую пользователь может использовать для предусмотренных системой действий в текущий момент.

### Резервирование средств — Funds Reservation

Временное ограничение доступности суммы для определённой операции. Это не обязательно означает фактическое движение денег во внешней платёжной системе.

### Освобождение резерва — Funds Release

Снятие ограничения с ранее зарезервированной суммы, после которого она снова становится доступной согласно правилам системы.

### Сверка — Reconciliation

Сопоставление данных об операциях и суммах между источниками, например внутренним учётом мерчанта и отчётом платёжного провайдера.

## Жизненный цикл платежа

### Жизненный цикл операции — Transaction Lifecycle

Последовательность состояний и событий, через которые проходит операция от создания до завершения.

### Состояние — State

Текущее положение операции в процессе обработки, например created, processing или succeeded. Значение определяется правилами конкретной системы.

### Переход состояния — State Transition

Изменение состояния операции при определённом событии и выполнении необходимых условий.

### Тестирование переходов состояний — State Transition Testing

Техника тест-дизайна, при которой проверяют состояния системы, переходы между ними и поведение при допустимых и недопустимых последовательностях событий.

### Промежуточный статус — Intermediate Status

Состояние, в котором окончательный результат операции ещё не определён или требуется дальнейшее действие.

### Конечный статус — Terminal Status

Состояние, из которого в рамках определённой модели операции дальнейшие переходы не предусмотрены. Последующие возвраты или споры могут учитываться отдельными связанными процессами.

### История статусов — Status History

Последовательность изменений состояния операции с доступными сведениями о времени и причинах переходов.

### Повторное зачисление — Duplicate Credit

Ошибочное увеличение баланса несколько раз по одной операции, которая должна быть учтена однократно.

## Webhook и возврат пользователя

### Webhook

HTTP-уведомление, отправляемое одной системой на заранее определённый адрес другой системы при наступлении события.

### Получатель webhook — Webhook Endpoint

Адрес и серверный обработчик, принимающий уведомления от внешней системы.

### Перенаправление — Redirect

Механизм перехода браузера на другой адрес. В платёжном сценарии может использоваться для возвращения пользователя со страницы провайдера на сайт мерчанта.

### URL возврата — Return URL

Адрес, на который пользователя возвращают после взаимодействия с внешним сервисом. Сам факт перехода на этот адрес не подтверждает успешный платёж.

### Опрос статуса — Polling

Периодические запросы к системе для получения актуального состояния операции.

### Событие — Event

Зафиксированный факт изменения или действия в системе, например успешное завершение платежа.

### Подпись webhook — Webhook Signature

Значение, позволяющее проверить подлинность уведомления и целостность подписанных данных по правилам конкретной интеграции.

### Повторная доставка — Retry / Redelivery

Повторная отправка уведомления. Она может выполняться автоматически при ошибке доставки или запускаться вручную предусмотренным инструментом.

### Подтверждение приёма — Acknowledgement

Ответ получателя, который отправитель трактует согласно контракту доставки. Он не обязательно означает завершение всей последующей бизнес-обработки.

## Идемпотентность и повторные запросы

### Идемпотентность — Idempotency

Свойство операции, при котором её повторное выполнение имеет тот же предусмотренный эффект, что и однократное выполнение. Ответы при этом не обязательно должны полностью совпадать.

### Ключ идемпотентности — Idempotency Key

Значение, позволяющее системе распознать повтор конкретной операции и обработать его по установленным правилам.

### Повтор запроса — Retry

Повторная отправка запроса, например после таймаута или обрыва соединения. Без соответствующей защиты повтор может привести к дополнительной операции.

### Дедупликация — Deduplication

Обнаружение и устранение повторной обработки одних и тех же данных, запросов или событий по выбранным признакам.

### Дублирующая операция — Duplicate Operation

Лишняя операция, созданная или выполненная повторно вместо однократной обработки исходного действия.

### Конкурентные запросы — Concurrent Requests

Запросы, обработка которых пересекается по времени. Они могут обращаться к одним данным и влиять на результаты друг друга.

### Состояние гонки — Race Condition

Ошибка, при которой результат зависит от взаимного порядка или времени выполнения параллельных действий.

## Этапы карточного платежа

### Аутентификация плательщика — Cardholder Authentication

Проверка того, что операцию выполняет законный держатель карты. Может проводиться с использованием 3D Secure.

### 3D Secure — 3DS

Протокол дополнительной аутентификации при карточных платежах. В зависимости от сценария может потребовать действия пользователя или пройти без дополнительного запроса к нему.

### Авторизация платежа — Payment Authorization

Одобрение карточной операции банком-эмитентом, обычно сопровождаемое резервированием соответствующей суммы.

### Банк-эмитент — Issuing Bank / Issuer

Банк, выпустивший карту пользователя и принимающий решение об одобрении карточной операции.

### Списание авторизованной суммы — Capture

Операция списания суммы в рамках ранее полученной авторизации. Может выполняться автоматически или отдельным запросом.

### Раздельная авторизация и списание — Separate Authorization and Capture

Схема, при которой сначала получают авторизацию и резервируют средства, а capture выполняют позже.

### Срок действия авторизации — Authorization Validity Period

Период, в течение которого авторизация остаётся действительной и позволяет выполнить capture по правилам провайдера и платёжной системы.

### Расчёты — Settlement

Процесс финансовых расчётов между участниками платежа. Его не следует отождествлять с подтверждением пользователя или одним лишь резервированием средств на карте.

## Этапы карточного платежа

### Аутентификация плательщика — Cardholder Authentication

Проверка того, что операцию выполняет законный держатель карты. Может проводиться с использованием 3D Secure.

### 3D Secure — 3DS

Протокол дополнительной аутентификации при карточных платежах. В зависимости от сценария может потребовать действия пользователя или пройти без дополнительного запроса к нему.

### Авторизация платежа — Payment Authorization

Одобрение карточной операции банком-эмитентом, обычно сопровождаемое резервированием соответствующей суммы.

### Банк-эмитент — Issuing Bank / Issuer

Банк, выпустивший карту пользователя и принимающий решение об одобрении карточной операции.

### Списание авторизованной суммы — Capture

Операция списания суммы в рамках ранее полученной авторизации. Может выполняться автоматически или отдельным запросом.

### Раздельная авторизация и списание — Separate Authorization and Capture

Период, в течение которого авторизация остаётся действительной и позволяет выполнить capture по правилам провайдера и платёжной системы.

## Тестирование 3D Secure

### 3D Secure — 3DS

Протокол аутентификации держателя карты при онлайн-платежах. Результат аутентификации необходимо отличать от результата самого платежа.

### Frictionless Flow

Сценарий 3DS, при котором аутентификация проходит без дополнительного действия пользователя.

### Challenge Flow

Сценарий 3DS, при котором пользователь должен выполнить дополнительное действие для подтверждения личности.

### Одноразовый код — One-Time Password / OTP

Код ограниченного срока действия, используемый для однократного подтверждения. Это один из возможных способов аутентификации.

### Подтверждение в банковском приложении — Out-of-Band Authentication

Подтверждение через отдельный канал, например банковское приложение, пока платёж оформляется в браузере.

### Прерывание сценария — Abandonment

Ситуация, когда пользователь прекращает прохождение сценария. Само прерывание не определяет окончательный финансовый результат операции.

### Тестовая среда — Sandbox / Test Environment

Среда для проверки интеграции с использованием предусмотренных тестовых данных и сценариев без выполнения обычных реальных платежей.

### Тестовая карта — Test Card

Предоставленные провайдером карточные данные для воспроизведения определённого поведения в тестовой среде, например запроса 3DS или отказа платежа.
